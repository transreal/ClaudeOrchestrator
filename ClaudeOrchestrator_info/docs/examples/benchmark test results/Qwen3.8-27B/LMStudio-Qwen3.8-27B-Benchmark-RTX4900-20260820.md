# LM Studio / Qwen3.8-27B 速度ベンチマーク（RTX 4090）

計測日: 2026-08-20 / 対象: localhost:1234 の LM Studio サーバ

---

## 1. 結論サマリ

| 項目 | 評価 |
|---|---|
| 全層 GPU オフロード | 正常。理論帯域上限の 86% に到達しており最適 |
| Context 40192 / Flash Attention / Unified KV / batch 2048-512 | いずれも妥当。変更不要 |
| **MTP 投機デコード** | **バッチ処理を 2.5 倍遅くしている。用途次第で切るべき** |
| **Enable Thinking（オン）** | **生成トークンの 85% が思考トークン。最大の速度要因** |
| VRAM 余裕 | 23.07 / 24.56 GB（94%）とやや逼迫。これ以上コンテキストを伸ばさない |
| サンプリング設定（温度 1.0 等） | 速度には無関係。品質面は今回未検証 |

用途を「対話」と「バッチ」で分けるのが最も効果的。バッチ側は設定変更だけで **2.4 倍** になる。

## 2. 計測環境

### ハードウェア / ランタイム

| 項目 | 値 |
|---|---|
| GPU | NVIDIA GeForce RTX 4090 / 24,564 MiB / driver 610.62 |
| バックエンド | llama.cpp-win-x86_64-nvidia-cuda12-avx2 **v2.29.1** |
| モデル | `lmstudio-community/Qwen3.8-27B-GGUF` |
| 量子化 / arch | Q4_K_M / `qwen35`（type: vlm） |
| ファイルサイズ | 本体 16 GB（ロード時 16.52 GiB）+ mmproj BF16 889 MB |
| max_context | 262,144（ロード時 40,192） |
| capabilities | `tool_use`（`reasoning` フィールドは非公開） |

### 計測時の llama-server 起動フラグ（＝スクリーンショットの設定）

```
--ctx-size 40192       --n-gpu-layers 999999    --n-cpu-moe 0
--ctx-checkpoints 32   --batch-size 2048        --ubatch-size 512
--threads 12           --parallel 4             --flash-attn on
--cache-type-k f16     --cache-type-v f16       --kv-offload  --kv-unified
--load-mode mmap+mlock
--spec-type draft-mtp  --spec-draft-n-max 2  --spec-draft-n-min 0  --spec-draft-p-min 0.75
```

`--n-gpu-layers 999999` = GUI の「GPU Offload 65」は全層オフロードに相当。

### 計測方法

- `POST /api/v0/chat/completions`（非ストリーミング）。速度はサーバ返却の `stats` を使用。
- **プレフィックスキャッシュ対策**: 全リクエストの先頭に一意な nonce 文字列を付与し、
  プロンプトキャッシュにヒットしないようにした（ヒットすると prefill が非現実的に速く出る）。
- 各セット冒頭にウォームアップを 1 回実施。
- 設定変更は `lms load` で行い、最後に元設定へ戻して**元の数値が再現することを確認**した
  （下表 A と D）。これにより A/B 比較の妥当性を担保している。

### 評価

- 16.52 GiB のモデルを 1008 GB/s の帯域で回した場合の理論上限は約 56 tok/s。実測 48 tok/s は

- 32k コンテキストでも生成速度が 46 tok/s とほとんど落ちない（Flash Attention が効いている）。
- 32k 投入時の TTFT は 10.3 秒。長文貼り付け時の待ち時間はここで決まる。

## 4. 設定 A/B 比較

### 4.1 単一ストリーム生成速度（tok/s）

| 設定 | 短文/512 | 8k/256 | 32k/256 |
|---|---:|---:|---:|
| **A. 現行（parallel=4, MTP=2）** | 47.62 | 52.13 | 46.63 |
| D. 現行を再ロードして再現確認 | 49.71 | 47.79 | 45.68 |
| B. MTP OFF, parallel=4 | 44.29 | 43.26 | 40.89 |
| C. MTP=2, parallel=1 | 48.60 | 52.27 | 50.30 |

MTP による単一ストリームの利得は **+10% 程度**（42〜44 → 48〜52）。

### 4.2 同時実行スケーリング（アグリゲート tok/s）

| 同時実行数 N | MTP=2, par=4（現行） | MTP OFF, par=4 | **MTP OFF, par=8** | MTP=2, par=8 | MTP=4, par=8 |
|---:|---:|---:|---:|---:|---:|
| 1 | 42〜48 | 42.14 | 42.49 | 20.06 | 22.51 |
| 2 | — | 74.26 | 74.14 | 38.71 | 23.97 |
| 4 | **58.65〜62.18** | 116.08 | 116.49 | 42.76 | 22.03 |
| 6 | — | 89.33 (※) | 140.02 | 43.74 | 21.54 |
| 8 | — | 110.99 (※) | **150.31** | 42.20 | 22.62 |

※ parallel=4 ではスロット不足で待ち行列が発生し、N=6 以降は頭打ち。

参考: MTP OFF, par=8 の 1 ストリームあたり速度は N=1 で 44.5 → N=8 で 22.9 tok/s。
総スループットと引き換えに個別応答は遅くなる。

### 4.3 MTP 投機デコードの挙動

- **ドラフト採択率は良好**: 実測 69〜97%（例: draft 40 / accepted 32 / rejected 8 = 80%）。
  採択率が悪いわけではない。
- にもかかわらず利得が +10% に留まり、並列時は逆効果になる。
  **オーバーヘッドが並列スロット数に比例して悪化する**のが原因で、
  parallel=8 では単一ストリームですら 20 tok/s まで落ちた（本来 44 tok/s）。
- `Max draft tokens` を 2 → 4 に増やすと全条件で 22 tok/s に固定される**壊滅的な劣化**。
  現行の **2 が既に最適値**であり、増やしてはいけない。

## 5. Thinking（推論トークン）のコスト

Enable Thinking がオンのため、全応答に `reasoning_content` が付く。

| タスク | 生成トークン | うち思考 | 実際の答え | 所要 |
|---|---:|---:|---:|---:|
| 17×23 を計算 | 62 | 56 | 3 文字 | 1.04 s |
| 感情分類（1 語で回答） | 186 | **182** | 7 文字 | 4.05 s |
| JSON 抽出 | 168 | 129 | 72 文字 | 2.75 s |
| 2 文で要約 | 224 | 180 | 209 文字 | 3.23 s |
| **合計** | **640** | **547（85%）** | | 11.07 s |

**GPU 設定のどの項目よりも大きな速度要因**。分類タスクでは 7 文字の答えのために 182 トークンを消費している。

### 無効化手段の検証結果

| 手段 | 結果 |
|---|---|
| プロンプト末尾に `/no_think` | **効かない**（思考率 82% のまま。合計 519 トークン中 423 が思考） |
| `chat_template_kwargs: {"enable_thinking": false}` | **効かない**（`/api/v0`・`/v1` の両エンドポイントで無視される） |
| GUI の Enable Thinking トグル | **これが唯一の制御手段**（サーバ側グローバル設定） |

Qwen3.8 のチャットテンプレートが旧来の `/no_think` マーカーを解釈しないため。

## 6. VRAM 実測

`lms load --estimate-only` はコンテキスト長を変えても 16.52 GiB 固定を返す（Confidence: LOW、
KV キャッシュを勘定していない）ため、実測した。

| 状態 | VRAM 使用量 |
|---|---:|
| モデル未ロード（デスクトップアプリのみ） | 1,405 MiB |
| ctx=40,192 ロード時 | **23,073 MiB** |
| ctx=131,072 ロード時 | 24,109 MiB |
| GPU 総容量 | 24,564 MiB |

- 現行 ctx=40,192 で **使用率 94%**、余裕は約 1.5 GB。
- ctx=131,072 では残り 455 MiB となり **危険なので上げないこと**。
- `--kv-unified` のおかげで **parallel を 4 → 8 にしても VRAM は増えない**（16.52 GiB のまま）。
  これが「parallel=8 が実質ノーコスト」である根拠。
- vision 用 mmproj（889 MB）が常時ロードされている。画像を使わないなら GUI で切ると余裕ができる。

## 7. 推奨設定

### バッチ処理向け（SourceVault 要約・派生推定など）— 現行比 2.4 倍

```bash
lms load qwen3.8-27b -c 40192 --gpu max --parallel 8 --ttl 3600 --no-speculative-draft-mtp -y
```

62 tok/s → **150 tok/s**。あわせて GUI の Enable Thinking をオフにすると更に効く。

### 対話向け（応答性重視）

```bash
lms load qwen3.8-27b -c 40192 --gpu max --parallel 2 --ttl 3600 --speculative-draft-mtp --speculative-draft-max-tokens 2 -y
```

MTP を残して単一ストリーム 48〜52 tok/s を確保しつつ、並列スロットを絞って MTP の
オーバーヘッド増大を回避する。

### 変更不要な項目

Context Length 40192 / Flash Attention オン / Unified KV Cache オン / KV を GPU に配置 /
Evaluation Batch 2048 / Physical Batch 512 / GPU Offload 65（全層）/ Context Checkpoints 32 /
Keep Model in Memory / Try mmap() / K・V Cache Quantization オフ（f16）。

## 8. 未検証・留意事項

- **サンプリング設定の品質影響は未検証**。今回は速度のみを計測した。
  温度 1.0・top_k 40・repeat penalty 1.1 は速度には影響しないが、Qwen3 系で一般に推奨される値
  （温度 0.6〜0.7、top_k 20、min_p 0、repeat penalty なし）からは外れている。
  出力品質に不満が出た場合の調整候補。
- 本計測はデスクトップアプリ（Edge / Steam / Adobe / Mathematica FE 等）が起動した状態で行った。
  アイドル時の VRAM 消費は 1.4 GB 程度だが、GPU を使うアプリを併用すると
  共有メモリへのスピルで大幅に低下する可能性がある。
- 計測後、**モデルは元の設定（parallel=4, MTP draft=2, ctx=40192）に復元済み**。
  ただし GUI の Load タブの保存値は CLI 再ロードの影響を受けている可能性があるため、
  Flash Attention / Unified KV / batch サイズは GUI 側で一度確認することを推奨する。
