# LM Studio / Qwen3.8-27B 速度ベンチマーク（AMD Ryzen AI Max+ 395 / Strix Halo）

計測日: 2026-08-20 / 対象: localhost:1234 の LM Studio サーバ（ホスト STRIXHALO128）

姉妹レポート: `LMStudio-Qwen3.8-27B-Benchmark-RTX4900-20260820.md`（RTX 4090）。
**同一モデルだが量子化（Q6_K / Q4_K_M）とバックエンド（Vulkan / CUDA）が異なる**ため、
数値を直接比較する際は §9 の注記を必ず併せて読むこと。

---

## 1. 結論サマリ

| 項目 | 評価 |
|---|---|
| 全層 GPU オフロード | 正常。帯域理論上限の 85% に到達しており最適 |
| **MTP 投機デコード** | **単一ストリームを 1.87 倍にしている。このマシンでは絶対に切ってはいけない** |
| MTP Max Draft = 2 | 妥当。4 まで同等、6 で劣化、1 でも劣化。変更不要 |
| **K/V Cache Quantization Q8_0** | **速度利得ゼロ・節約は 1.2 GB のみ。VRAM が 64 GB もあるので払う意味がない。OFF 推奨** |
| Flash Attention / Unified KV / Context 40000 | いずれも妥当。変更不要 |
| **Physical Batch Size 512** | **prefill は batch を小さくするほど速い。128 にすると +11%** |
| **prefill 141 tok/s** | **本機最大の弱点。設定では動かない（全 A/B で 129〜151 tok/s）。ハード/バックエンド由来** |
| VRAM 余裕 | 28.5 / 65.5 GB（44%）。最大コンテキスト 262,144 でも 37.1 GB。**制約になっていない** |
| Enable Thinking（オン） | 生成トークンの 85% が思考トークン。4090 と同じ傾向 |
| サンプリング設定（温度 1.0 / repeat penalty 1.1） | 速度には無関係。Qwen3 系の推奨から外れており品質面の調整候補 |

**結論は 4090 と正反対**。4090 では「MTP を切るとバッチが 2.4 倍速くなる」だったが、
本機では **MTP を切ると単一ストリームが半分の速度になる**。
4090 側の設定指針をこのマシンに持ち込んではいけない。

本機の律速は生成ではなく **prefill（プロンプト読み込み）**。長文を投げる用途では
21k トークンで TTFT が 2 分半かかる。設定変更では解決しないので、
**プロンプトを短く保つ運用**が唯一の実効的な対策になる。

  （§4.1 の Z 行が復元後の再現確認）。

## 3. 単一ストリーム性能（現行設定）

| prompt | 生成 | TTFT | 実効 prefill | 生成速度 |
|---:|---:|---:|---:|---:|
| 99 | 132 | 6.554 s | (25.8) | 15.73 tok/s |
| 781 | 173 | 13.597 s | (71.8) | 17.36 tok/s |
| 2,850 | 256 | 26.679 s | 119.0 tok/s | 15.06 tok/s |
| 5,556 | 173 | 44.686 s | 132.4 tok/s | 14.90 tok/s |
| 10,730 | 256 | 80.510 s | 137.9 tok/s | 15.95 tok/s |
| 21,110 | 165 | 155.835 s | 137.9 tok/s | 13.53 tok/s |

括弧付きは固定オーバーヘッド支配のため参考値。実効 prefill は約 138 tok/s に収束する。
両端の傾きから **TTFT ≒ 5.85 s + プロンプト長 / 141 tok/s**。

### 評価

- 21.76 GiB のモデルを 256 GB/s（LPDDR5X-8000 / 256-bit）で回した場合の理論上限は
  約 11.0 tok/s。**MTP を切った実測 9.3 tok/s はその 85%** にあたり、
  全層オフロードが正しく効いていることを示す（4090 の 86% とほぼ同じ効率）。
- MTP 有効時の 15〜17 tok/s は理論帯域上限を超えている。これは投機デコードが
  1 回の重み読み出しで複数トークンを検証するためで、**MTP が正常に効いている証拠**。
- 生成速度は同一設定でも 13.5〜17.6 tok/s とばらつく（±15%）。電力/温度由来と推定。
  §4 の A/B は 1 サンプルずつなので、**5% 未満の差は有意ではない**と考えること。
- 21k コンテキストでも生成速度はほとんど落ちない（Flash Attention が効いている）。

### TTFT の固定コスト

キャッシュ完全ヒット（同一プロンプト連投）でも TTFT は縮まない。

| 条件 | TTFT |
|---|---|
| 同一プロンプト連投 5 回（間隔なし） | 3.26 → 3.01 → 2.95 → 2.96 → 2.92 s |
| 30 秒アイドル後 | 2.90 / 2.77 s |

- **アイドル復帰コストではなく、リクエスト毎の固定費が約 2.9 秒**存在する。
- MTP OFF・KV f16・FA OFF など全 A/B で 2.7〜3.2 秒であり、**設定では動かない**。
- 参考: 4090 は 105 トークンのプロンプトで TTFT 0.195 秒。
- curl 実測の壁時計は 3.45〜3.62 秒で、サーバ申告値とほぼ整合（超過 0.23 秒）。

### おまけ: `localhost` の名前解決コスト

| 接続先 | TCP connect |
|---|---:|
| `http://localhost:1234` | 0.205 s |
| `http://127.0.0.1:1234` | 0.0006 s |

`localhost` は IPv6 先行解決のため**毎リクエスト 205 ms を無駄に払う**。
クライアント側は必ず `127.0.0.1` を使うこと。

## 4. 設定 A/B 比較

すべて ctx=40,000 / parallel=1。生成速度は 192 トークン生成時のサーバ申告値。

### 4.1 単一ストリーム

| 設定 | 生成 tok/s | 実効 prefill | TTFT 床 | draft 採択 | VRAM |
|---|---:|---:|---:|---:|---:|
| **A. 現行**（MTP=2 / KV q8_0 / FA on / Uni off） | **17.40** | 143.6 | 2.72 s | 108/165 (65%) | 28.61 GB |
| B. KV f16（量子化 OFF） | 17.46 | 145.0 | 2.77 s | 108/165 (65%) | 29.74 GB |
| C. MTP OFF | **9.30** | 148.3 | 2.79 s | — | 27.67 GB |
| D. MTP OFF + KV f16 | 9.32 | 148.2 | 3.00 s | — | 28.78 GB |
| E. Unified KV ON | 16.57 | 145.2 | 3.03 s | 104/171 (61%) | 29.72 GB |
| F. Flash Attention OFF | 17.13 | 140.3 | 3.00 s | 107/168 (64%) | **33.56 GB** |
| G. MTP Max Draft = 4 | 17.64 | 142.7 | 3.20 s | 116/244 (48%) | 28.84 GB |
| H. MTP Max Draft = 6 | **13.21** | 143.0 | 3.19 s | 124/396 (31%) | 29.18 GB |
| I. MTP Max Draft = 1 | 14.31 | 141.7 | 2.98 s | 81/109 (74%) | 28.43 GB |
| Z. 現行設定へ復元して再現確認 | 14.36 | 143.2 | 3.16 s | 92/197 (47%) | 28.59 GB |

読み取れること:

- **MTP が唯一の大レバー**。OFF で 17.4 → 9.3 tok/s と **46% 減**。
  4090 では MTP の利得は +10% に過ぎなかったが、本機では **+87%**。
- **KV 量子化 Q8_0 は速度に無関係**（17.40 vs 17.46 は誤差範囲）。
  得られるのは 1.13 GB の節約のみ。
- Unified KV は parallel=1 では利得なし（むしろ微減）。現行の OFF が正しい。
- Flash Attention OFF は速度ほぼ同じだが **VRAM が 5 GB 増える**。現行の ON が正しい。
- **prefill は全設定で 140〜148 tok/s**。KV 量子化・MTP・Unified KV・FA のどれを触っても動かない。
- Z 行の生成速度 14.36 は A 行 17.4 より低いが、prefill 143.2（vs 143.6）と
  VRAM 28.59 GB（vs 28.61）は一致しており、**復元は成功**。差は前述の ±15% のばらつき。

### 4.2 バッチサイズと prefill

prefill だけは Physical Batch Size に反応する。**小さいほど速い**（Vulkan バックエンドの特性）。
約 6,900 トークンのプロンプトを 3 回投入した実効 prefill の中央値。

| Physical Batch | 実効 prefill（中央値） | 3 回の実測 | 現行比 |
|---:|---:|---|---:|
| 64 | 150.6 tok/s | 167.4 / 150.6 / 150.3 | +9.4% |
| **128** | **153.0 tok/s** | 168.6 / 153.0 / 152.3 | **+11.1%** |
| 256 | 144.5 tok/s | 162.2 / 144.4 / 144.5 | +4.9% |
| **512（現行）** | **137.7 tok/s** | 153.7 / 137.7 / 137.2 | — |
| 1,024 | 134.9 tok/s | 1 サンプルのみ | −2.0% |
| 2,048 | 129.1 tok/s | 1 サンプルのみ | −6.2% |

- 各組の 1 回目だけ高く出るのはウォームアップの影響。中央値で比較すること。
- **128 が最適**で、現行の 512 から **+11%**。64 まで下げると再び落ちるので下げ過ぎは無効。
- Evaluation Batch を 2,048 → 4,096 にしても効果なし（129.7 tok/s で physical 2,048 と同等）。
  効くのは Physical Batch だけ。
- 生成速度には影響しない（どの設定でも 16.7〜18.2 tok/s の範囲）。
- ただし 21k トークンの TTFT が 156 秒 → 140 秒になる程度で、
  **prefill が遅いという本質は解決しない**。

### 4.3 同時実行スケーリング（parallel=4 でロード）

| 同時実行数 N | MTP ON アグリゲート | MTP OFF アグリゲート | MTP ON ストリーム毎 | MTP OFF ストリーム毎 |
|---:|---:|---:|---:|---:|
| 1 | 8.90 | 6.00 | 17.26 | 9.38 |
| 2 | 12.06 | 9.36 | 13.24 | 8.57 |
| 4 | 12.38 | **14.72** | 5.65 | 7.23 |

- アグリゲートは TTFT を含む壁時計基準（総生成トークン ÷ バースト全体の所要時間）。
  ストリーム毎はサーバ申告の生成速度（TTFT を含まない）。
- **N=4 では MTP OFF が MTP ON を上回る**。この点だけは 4090 と同じ傾向。
- ただし利得は現行比 **1.65 倍**（8.90 → 14.72）に留まる。4090 の 2.4 倍・150 tok/s とは
  桁が違うので、「バッチ処理をこのマシンに寄せる」という判断は成り立たない。

### 4.4 MTP 投機デコードの挙動

- ドラフト採択率は Max Draft の設定で変わる: 1→74% / 2→65% / 4→48% / 6→31%。
- 速度は **2〜4 が最適**（17.4〜17.6 tok/s）。6 では採択率が落ちて 13.21 tok/s まで劣化。
  1 でも 14.31 tok/s と足りない。
- 4090 で観測された「Max Draft を 4 にすると全条件 22 tok/s に固定される壊滅的劣化」は
  **本機では再現しない**。とはいえ現行の 2 が最適域なので変更する理由もない。

## 5. Thinking（推論トークン）のコスト

Enable Thinking がオンのため、全応答に `reasoning_content` が付く。
以下はモデルが返した `reasoning_tokens` の実数。

| タスク | 生成トークン | うち思考 | 実際の答え | 所要 |
|---|---:|---:|---:|---:|
| 17×23 を計算 | 67 | 61 | 5 文字 | 8.90 s |
| 感情分類（1 語で回答） | 79 | **75** | 9 文字 | 13.29 s |
| JSON 抽出 | 241 | 209 | 60 文字 | 21.39 s |
| 2 文で要約 | 197 | 151 | 255 文字 | 21.26 s |
| **合計** | **584** | **496（84.9%）** | | **64.84 s** |

4090 の 85% とほぼ同じ比率。分類タスクでは 9 文字の答えのために 75 トークンを消費している。
本機は生成が 4090 の 1/3 の速度なので、**思考トークンの絶対コストは 3 倍痛い**。

### 無効化手段の検証結果

| 手段 | 結果 |
|---|---|
| プロンプト末尾に `/no_think` | **効かない**（思考率 89.1%。合計 801 トークン中 714 が思考で、むしろ増加） |
| `chat_template_kwargs: {"enable_thinking": false}` | **効かない**（思考率 84.1% で既定と変わらず） |
| GUI の Enable Thinking トグル | **これが唯一の制御手段**（サーバ側グローバル設定） |

4090 と同一の結論。Qwen3.8 のチャットテンプレートが `/no_think` を解釈しないため。

## 6. VRAM 実測

統合メモリのうち 64 GB を VRAM に割当。GPU Adapter Memory の Dedicated Usage を実測した。

| 状態 | VRAM 使用量 |
|---|---:|
| モデル未ロード（デスクトップアプリのみ） | 4,670 MB |
| ctx=40,000（KV q8_0）＝ **現行** | **28,520 MB** |
| ctx=40,000（KV f16） | 29,740 MB |
| ctx=131,072（KV q8_0） | 31,960 MB |
| ctx=262,144（KV q8_0・モデル上限） | 37,100 MB |
| ctx=40,000・Flash Attention OFF | 33,560 MB |
| VRAM 割当総量 | 65,536 MB |

- 現行 ctx=40,000 で **使用率 44%**、余裕は約 37 GB。
- **モデル上限の 262,144 まで上げても 37.1 GB（57%）**で収まる。
  4090 の「94% 逼迫・これ以上伸ばすな」とは真逆で、**メモリは全く制約になっていない**。
- KV キャッシュは q8_0 で約 37.8 kB/token。q8_0 → f16 で 2 倍（40k で 1.2 GB → 2.4 GB）。
- したがって **K/V 量子化で節約している 1.2 GB には何の意味もない**。
- Flash Attention を切ると 5 GB 増える。切る理由はない。
- vision 用 mmproj が常時ロードされている。画像を使わないなら GUI で切ると余裕ができるが、
  本機ではメモリが余っているので優先度は低い。

## 7. 推奨設定

### 7.1 変更を推奨する項目

| 項目 | 現行 | 推奨 | 理由 |
|---|---|---|---|
| K Cache Quantization | Q8_0 | **OFF（f16）** | 速度差ゼロ。節約 1.2 GB は 37 GB 余っている本機では無価値。量子化 KV は品質を落とすだけ損 |
| V Cache Quantization | Q8_0 | **OFF（f16）** | 同上 |
| Physical Batch Size | 512 | **128** | prefill が +11%。本機唯一の弱点への数少ない有効打（§4.2）。生成速度・VRAM への副作用なし |

### 7.2 現状維持でよい項目（実測で確認済み）

- **MTP Speculative Decoding オン / Max Draft 2** — 切ると半速。増やす利得もない。**触らないこと**
- Flash Attention オン（OFF は VRAM +5 GB で利得なし）
- Unified KV Cache オフ（ON は微減）
- Context Length 40,000（VRAM 的には 262,144 まで上げられるが、prefill 141 tok/s では
  131k 投入に約 15 分かかり実用にならない。**制約はメモリではなく prefill 速度**）
- Max Concurrent 1（並列化の利得が薄い。§7.3 参照）
- GPU Offload 65（全層）/ Keep Model in Memory オン / mmap() オフ（ロード 9〜10 秒）
- CPU Thread Pool 12 / Evaluation Batch 2048

### 7.3 バッチ処理を回す場合

```bash
lms load qwen3.8-27b -c 40000 --gpu max --parallel 4 -y
```

さらに GUI で MTP をオフにすると、アグリゲート 8.9 → 14.7 tok/s（**1.65 倍**）。
ただし対話用途では MTP オフは 46% の速度低下になるので、**プロファイルを分けること**。
利得が 4090 ほど大きくないので、常用設定を変えてまで追う価値があるかは用途次第。

### 7.4 クライアント側

- エンドポイントは `http://127.0.0.1:1234` を使う（`localhost` は毎回 205 ms を浪費）。
- **プロンプトを短く保つことが最大の最適化**。TTFT ≒ 5.85 s + N/141 なので、
  10k トークンの文脈を毎回投げると 1 リクエストあたり 1 分 15 秒が prefill に消える。
- 同じ前置きを使い回す場合はプレフィックスキャッシュが効くよう、
  **可変部分をプロンプトの末尾に置く**こと（先頭に nonce や時刻を置くとキャッシュが全滅する）。

## 8. 未検証・留意事項

- **生成速度は同一設定でも 13.5〜17.6 tok/s（±15%）ばらつく**。電力・温度由来と推定。
  §4 の A/B は各 1 サンプルなので、5% 未満の差は有意ではない。
  MTP の 87%、Max Draft 6 の劣化、KV 量子化の無効果は、この幅を大きく超えるので有意。
- **出力品質は未検証**。今回は速度のみを計測した。
  温度 1.0 / repeat penalty 1.1 は Qwen3 系で一般に推奨される値（温度 0.6〜0.7、
  repeat penalty なし）から外れている。top_k 20 / min_p 0 は推奨どおり。
- **Q4_K_M 版は未検証**。生成は帯域律速なのでモデルサイズに反比例し、
  16 GB 版に替えれば約 1.46 倍（推定 13.6 tok/s、MTP 込みで 25 tok/s）になる見込み。
  品質とのトレードオフになるが、速度が問題なら最も効く一手。
- **ROCm ランタイムは未計測**。2.29.0 がインストール済みで prefill が改善する可能性はあるが、
  ROCm バックエンドでは qwen35 系ハイブリッドモデルで KV/プロンプトキャッシュ混入が発生し、
  それを避けるために Vulkan へ移行した経緯がある。**速度目的で戻すべきではない**。
- 本計測はデスクトップアプリが起動した状態で行った（アイドル時 VRAM 4.67 GB）。
- 計測後、**モデル設定は元の保存値へ復元し、バックアップと完全一致することを確認済み**。
  GUI の Load タブは CLI 再ロードの影響を受けている可能性があるため、
  Context 40000 / Flash Attention / KV 量子化 / MTP は GUI 側でも一度確認することを推奨する。

## 9. RTX 4090 との比較

**前提の違い**: 同じ Qwen3.8-27B だが、4090 側は **Q4_K_M（16 GB）+ CUDA**、
本機は **Q6_K（21.8 GiB）+ Vulkan**。生成速度は帯域律速なのでモデルサイズに反比例し、
本機を Q4_K_M に替えれば約 1.46 倍になる。
以下の比は**その補正を掛けていない実測どうしの比**である。

### 使い分けの指針

- **長文を投げる処理（要約・派生推定・RAG 応答）は 4090 に寄せる**。
  prefill が 17 倍違うため、10k トークンの文脈で TTFT が 4 秒 対 76 秒になる。
- **Strix Halo はメモリ容量が武器**。4090 に載らない大きなモデルを常駐させる用途でのみ優位。
  超長コンテキストは VRAM 的には載るが prefill 速度が実用性を殺すため、
  「大きなモデルを載せる」方向の方が現実的。
- **設定指針を共有してはいけない**。4090 の推奨（MTP オフ・parallel 8）を
  本機に適用すると単一ストリームが 46% 遅くなる。
